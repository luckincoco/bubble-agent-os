# Coding Workflow

结构化编码工作流，参照 addyosmani/agent-skills 的工程纪律。每次编码任务必须遵循以下 6 个阶段，每个阶段都有验证门，不可跳过。

## Process（6 阶段）

### 1. DEFINE — 澄清需求
- 追问模糊点，确认边界和约束
- 输出: 一句话目标 + 明确的验收标准
- **验证门**: 必须有可测试的验收标准才能进入下一步。如果用户需求模糊，先问清楚。

### 2. PLAN — 拆解任务
- 使用 `list_directory` 和 `read_file` 了解现有代码结构
- 垂直切片：每个任务是一个从上到下的完整路径，不超过 100 行改动
- 输出: 有序任务列表，每个任务标注影响的文件
- **验证门**: 每个任务有验收标准 + 影响文件列表。未读过相关文件不准开始规划。

### 3. BUILD — 逐片实现
- 一次只做一个切片
- 每个切片的循环: 实现 → 验证 → 下一个
- 用 `write_file` 写入，用 `read_file` 确认写入正确
- **验证门**: 每个切片完成后必须用 `shell_exec` 确认 build/lint 通过

### 4. VERIFY — 证明可用
- 运行测试: `shell_exec` 执行项目的测试命令
- 类型检查: `shell_exec` 执行 tsc --noEmit 或等价命令
- **验证门**: 必须有 shell_exec 的输出作为证据。"我觉得没问题"不是证据。

### 5. REVIEW — 质量检查
- 安全: 是否引入了注入、XSS、硬编码密钥？
- 简洁: 是否有不必要的抽象或过度工程？
- 一致: 是否与项目现有代码风格一致？
- **验证门**: 逐项确认无问题。如有问题回到 BUILD 修复。

### 6. SHIP — 完成交付
- 确认没有遗留 TODO 或半成品
- 用 `shell_exec` 执行 `git diff` 或 `git status` 展示最终变更
- 向用户汇报完成情况
- **验证门**: 所有切片的验收标准都已满足

## Anti-Rationalization（反合理化表格）

这不是可商量的。这不是可选的。你不能用合理化来逃避这些步骤。

| 借口 | 反驳 |
|------|------|
| "先写完再测试" | 不行。每个切片完成后必须验证。累积的错误比逐个修复贵 10 倍。 |
| "这个改动太小不需要测试" | 不行。任何改动都需要证据证明正确。小改动也会引入回归。 |
| "我知道这能用" | "知道"不是证据。`shell_exec` 的输出才是。运行它。 |
| "先全部写完，最后统一 review" | 不行。发现问题越晚修复成本越高。每个切片结束就 review。 |
| "这只是重构，不影响功能" | 不行。重构后 tsc + test 必须绿。重构就是要证明行为不变。 |
| "文件太多了读不完" | 用 `list_directory` + `read_file` 逐步读。假设 = 错误的开始。 |
| "用户没有测试，我也不用写" | 至少运行 `tsc --noEmit` 或 lint。零验证 = 零信心。 |
| "我先把代码写了，验证门以后再过" | 不行。验证门是强制的检查点，不是建议。跳过 = 违规。 |

## Red Flags（危险信号）

如果出现以下情况，立即停下来检查：
- 一次修改超过 3 个文件但没有分步验证
- 没有运行过任何 shell_exec 命令就说"完成了"
- 假设文件内容而没有先 `read_file`
- 跳过 DEFINE 直接开始写代码
- BUILD 阶段没有产生任何 `write_file` 调用
- VERIFY 阶段没有产生任何 `shell_exec` 调用
